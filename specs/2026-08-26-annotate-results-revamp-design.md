# Annotate results revamp

**Date:** 2026-08-26
**Status:** approved

> Spec location note: the skill default is `docs/superpowers/specs/`, but `docs/`
> is this repo's pkgdown build output — gitignored in full, with nothing tracked
> under it, and regenerated by `pkgdown::build_site()`. A spec placed there would
> be untracked and eventually clobbered. Specs live in `specs/` instead.

## Problem

The Annotate results page has three faults, reported together:

1. **The page is too long.** Results are spread over three stacked cards — dot
   plot, signature table, gene sets table — so reading one signature's gene sets
   means scrolling past everything else.
2. **The dot plot is too big.** A three-signature run renders at 1114×1611px
   (12.4in tall at 130dpi) and dominates the page. Content-based sizing fixed the
   earlier cramping but overcorrected.
3. **The dot plot's axis and legend read oddly.** The axis is reverse-log FDR
   with breaks like `1e-34`, most-significant-on-the-right. Two legends compete:
   dot colour encodes FDR while x position also encodes FDR, so colour is
   redundant.

All three are hypeR's own ggplot choices, inherited by rendering `hyp_dots()`
server-side to a PNG.

## Approach

Draw the chart in the browser as inline SVG, and keep hypeR's PNG available on
demand for figures. The gene sets move into expandable rows.

This is a presentation change. **The enrichment results model does not change**
— `/annotate/run` already returns per-signature entries carrying `info`,
`n_enriched` and `results`, which is everything the new UI needs. The one
response change is removing `dotplot_png`, which moves to its own route (§3).

## Components

### 1. `EnrichmentDotPlot` (new, `web/src/components/`)

Inline SVG, drawn from `EnrichmentRunSignature[]`. Sibling to the existing
`LeadingEdgePlot`, which established this pattern.

**Encoding — single signature:**
- y: gene set label, sorted most significant at top
- x: **−log10(FDR)**, ascending left→right, plain numeric ticks (0, 10, 20…)
- size: **overlap count**
- colour: none

Colour is dropped because x position already encodes significance; encoding it
twice is the redundancy behind "legend is confusing". One legend (size) remains.

**Encoding — multiple signatures:**
- y: gene set label
- x: signature (categorical), as `hyp_dots(merge = TRUE)` does
- size: overlap count
- colour: −log10(FDR)

Colour returns here because x can no longer carry significance. Two encodings,
both load-bearing.

**Sizing:** `viewBox` with `width: 100%`, height capped at ~420px, row count
driving the internal scale. Reflows on resize; cannot dominate the page.

**Interaction:** hover a dot for FDR, p-value, overlap and hit list.

### 2. Signature rows become expandable

One card replaces two. Each signature is a collapsed row:

    Signature · Signature Size · Enriched Genesets · Background

Expanding reveals, inline: that signature's `hyp$info` chips, its gene sets
table, and — for GSEA runs — the leading-edge plot nested in the row it belongs
to. The separate "Enriched gene sets" card is removed.

A single-signature run auto-expands its only row.

This mirrors `hypeR::rctbl_mhyp()`, which renders a multihyp as one row per
signature with `onClick = "expand"` and a `details =` callback — the structure
already adopted for the data model, now for the interaction too.

### 3. PNG moves behind a button

`GET /annotate/dotplot` renders hypeR's own `hyp_dots()` figure and returns it
as a PNG, driven by a **Download plot** button.

It takes the same inputs as `/annotate/run` — `api_key`, `signature_hashkeys`,
`test`, `species`, `collection`, `subcollection`, `fdr` — and re-runs the
enrichment to rebuild the hyp object. That is a deliberate trade: the
alternative is caching hyp objects server-side, which means holding per-caller
state in a single-process Plumber API for a button most runs never press. The
re-run costs about what the original did (~2s for a 972-gene signature against
Hallmark), and only when the button is clicked.

`/annotate/run` stops embedding `dotplot_png`. That field is currently a base64
blob in every response — 176KB on a three-signature run — paid for on every run
whether or not anyone looks at the figure.

The existing `render_hyp_dots_png()` moves to the new route unchanged, including
its object-shape branching and axis correction.

## Data flow

    POST /annotate/run  ->  { signatures: [ { info, n_enriched, results } ], skipped }
                              |                        |
                              v                        v
                    EnrichmentDotPlot        expandable signature rows
                     (inline SVG)             (gene sets + info + leading edge)

    GET /annotate/dotplot  ->  image/png   (only when Download plot is clicked)

## Error handling

- No signature enriched anything: chart is omitted, rows still render showing 0.
- A signature enriched nothing: its row expands to an empty-state message.
- `hyp_dots()` fails: the download returns a 502 with the reason. It can no
  longer silently blank part of the results page, because it is no longer on it.
- The chart never depends on the PNG route; a failed download leaves the page
  intact.

## Testing

- Reuse the four `render_hyp_dots_png()` regression tests against the new route,
  covering all three hypeR object shapes plus nothing-enriched.
- New: `/annotate/dotplot` returns `image/png`, and 404s an unknown signature.
- New: `/annotate/run` no longer carries `dotplot_png`.
- Browser: expand/collapse, auto-expand on a single-signature run, and the chart
  at 1, 2 and 3 signatures.

## Out of scope

- Changing which gene sets are enriched, or any statistics.
- The MCP server, which has its own `run_enrichment` and never consumed this
  shape.
- Rummagene and Compare, which have their own result surfaces.
